## Identity & ownership drift relevant to slice 2

### ID parsing (spec §2)
- **Out of scope for slice 2.** The four live `id.split("_")[0]` sites are `Sandbox_Engine.js:895`, `Override_Injector.js:100`, `Appender.js:90` (and `Override_Injector.js:65` for the substring-with-substring case called out in spec §10). The Sandbox reads occurrence IDs (e.g. `evId.split("_")[0]` at line 895 to build `routineKey = coreId + "^" + routeSig`). Touching these in slice 2 would balloon the diff and is not what the spec sub-items 0A/0C demand. **Decision: leave for a later slice.**
- Slice 2 *adds* a new positional column to the Sandbox's queue output and a new `block_stepN` to the typed protocol. This does not interact with `id.split("_")[0]` — IDs are not split on the new column; the column is a string-valued policy tag.

### Command handling (spec §9)
- **Out of scope for slice 2.** 0A/0C are about planning (`Sandbox_Engine.js` emission) and compilation (`Compiler.js` consumption), not command handling. The `TDS State Command` envelope and its adapters (`Override_Injector.js`, `Appender.js`, `Return_to_Base.js`, `Depart_Now.js`, `Unlock.js`, `Stop_Logger.js`) are not touched. **Decision: leave for Phase 4.**

### Single-writer contract (spec §8)
- **Sandbox_Engine.js** is the planning engine. It does not write any of the named persisted files in the writer table. Its only writes are `setLocal` (queue + meta) and `setGlobal('TDS_Lateness_Halt')` (a halt flag, not a writer violation). **No new write paths in slice 2.** Slice 2 changes the *shape* of the queue output (adds a column), not the file ownership.
- **Compiler.js** writes `Itin_Master.json` (one of its spec-named responsibilities) and `TDS_Overrides.json` (specifically `OVR['Depart_Memory']` at `Compiler.js:421-425`). The slice-1 verify-report already called out the `Depart_Memory` write as a known anti-pattern (it's the only place `TDS_Overrides.json` is written outside the override handler). Slice 2 must **not** make this worse — no new fields should be written to `TDS_Overrides.json`. The `departurePolicy` is a leg field on `Itin_Master.json`; it does not belong in the override store.
- The existing `pitstopState` / `_IN`-suffix / `EOD_RETURN` reconstruction is precisely the silent-state-inference the spec is forbidding. Once slice 2 emits `departurePolicy` and `Compiler.js` consumes it, the silent inference is removed and the per-leg `departurePolicy` becomes the authoritative source.

## Cache, cluster, override, API drift relevant to slice 2

### Sandbox → Compiler data path
- The Sandbox emits a positional queue via `setLocal('block_queue', queue.join("~"))` (`Sandbox_Engine.js:1222`) plus per-leg `block_step1`–`block_step16` values that the queue's consumer (an external Tasker native) splits and writes back. **No live script in the 18 reads `block_queue` directly** — confirmed by grep; the only writers are `Sandbox_Engine.js`. The `block_stepN` keys are what `Compiler.js` consumes (`Compiler.js:28-37`: `block_step1` actionType, `block_step3` dest, `block_step4` mode, `block_step5` evStartSecs fallback, `block_step7` pitstopState, `block_step8` apiType, `block_step9` apiUnix, `block_step10` evId, `block_step12` lateness, `block_step14` isAttachedDropin, `block_step15` targetDesc, `block_step16` pendingStopsRaw; `Compiler.js:40-41` reads `api_duration_secs` and `api_distance_miles`).
- Per the canonical spec §0.1 the typed protocol already names **`block_step17` (route duration seconds)**, **`block_step18` (route distance)**, **`block_step19` (departure policy)**. The slice-1 exploration confirmed *none* of these are emitted today. Slice 2's 0A work has two implementation choices — see "Open questions" below.
- `Finaliser.js` does **not** consume `departurePolicy`. It produces `TDS_Master.json` from the calendar variables and writes `TDS_Base_Geocodes.txt`; it does not see the planner's queue. **No 0A changes needed in Finaliser.**
- The route cache (Welford mean ± 1 SD via `RouteCache.txt`, RAM tier via `Temp_Route_Cache.txt`) is read by `Sandbox_Engine.js:getCachedTime` at line 451. **It does not influence the ASAP/JIT decision** — it only affects travel duration, not departure timing. **No cache changes needed for 0A or 0C.**

### Override store
- `TDS_Overrides.json` is shared among 6+ writers (per the first-slice audit, the override store is the "de-facto shared mutable bag"). Slice 2 must not add a new key. The `departurePolicy` is per-leg state; it lives on the leg in `Itin_Master.json`.

### Cluster
- `Finaliser.js:201-237` builds clusters from `validEvents`; it does not see the queue. No slice-2 changes needed.

## Logging & tests

### Logging
- No structured JSON logging exists today; the first-slice verify-report confirmed this. The canonical spec §17 requires `EVT-LIVE_BASE_OVERRIDES_LEGACY_ORIGIN` (for 0C) and `EVT-DEPARTURE_POLICY_FALLBACK_USED` (for 0A) as canonical event codes.
- Slice 2 should emit at minimum:
  - `EVT-LIVE_BASE_OVERRIDES_LEGACY_ORIGIN` whenever Sandbox consults live `User_At_Base` and that value contradicts the prior itinerary (warning, on the `oldItin.length > 0` branch when live `currentlyAtBase` is true and `simAtBase` was derived as false from the previous leg's `pitstopState`).
  - `EVT-DEPARTURE_POLICY_FALLBACK_USED` whenever Sandbox falls back from the explicit policy to a reconstructed one (e.g. when the queue is consumed but `block_step19` is missing — should never happen post-slice-2, but is the safety net for the migration).
- The first-slice pattern (`flash(JSON.stringify(event))`) is the available primitive. No new file, no new `setLocal`/`setGlobal` key. **Recommend staying with the flash pattern from slice 1.**

### Test surface
- The harness at `harness/` covers AC-8, AC-9, AC-10, and INV-0.6 with five `vm`-sandboxed Node scripts. The mock at `harness/mock_tasker.js` already exposes `setLocal`, `setGlobal`, `readFile`, `writeFile`, `flash`, and a pinned `Date`. **The existing harness surface is sufficient for AC-1 and AC-6.**
- For AC-1, the new test (`harness/test_compiler_ac1.js`) needs synthetic `TDS_Master.json`, `Itin_Master.json` (with a non-base previous leg), `TDS_Overrides.json` (minimal), and `block_step19` carrying the explicit `departurePolicy` the Sandbox would have emitted. It should assert: given a head leg with `block_step19="ASAP"`, `actualHeadDeparture === hardFloor` (no `Math.max(hardFloor, depTarget)`); given `block_step19="JIT"`, `actualHeadDeparture === Math.max(hardFloor, headLeg.depTarget)`. The `isPrevBase` reconstruction in `Compiler.js:160-168, 247-256` must be replaced with a direct read of the explicit policy.
- For AC-6, the new test (`harness/test_sandbox_ac6.js`) needs to run `Sandbox_Engine.js` directly (not the Compiler). It must seed:
  - `TDS_Master.json` with a single future event at `idx=1`
  - `Itin_Master.json` with a stale leg whose `pitstopState` says "handled" (simulating the prior itinerary says away)
  - `setGlobal('User_At_Base', 'true')` to simulate live says home
  - `setGlobal('Base_Arrival_Unix', nowSec.toString())`
  - `setGlobal('User_Loc', <home coords>)` matching `Home_Coords`

- A combined test (`harness/test_sandbox_compiler_ac1_ac6.js`) is feasible: AC-1 needs `Compiler.js` plus synthetic `block_stepN` locals; AC-6 needs `Sandbox_Engine.js` plus synthetic master/itin files. Two scripts are cleaner.

## Spec drift not covered above

- **Origin source enum (spec §3, `originSource`)** is a canonical field that the codebase does not emit today. The valid values per spec §3 are `ACTIVE_MANUAL_TRIP`, `ACTIVE_PLANNED_TRIP`, `LIVE_BASE`, `LIVE_LOCATION`, `CONFIRMED_LAST_DESTINATION`, `OVERNIGHT_BASE_RESET`, `LEGACY_ITINERARY_FALLBACK`. The current Sandbox tracks `User_At_Base` and a `pitstopState` string; neither maps 1:1 to the enum. Slice 2 must NOT introduce a full originSource enum migration (that's a Phase 1 typed-protocol task). But the priority chain in spec §0.3 (active manual → IN_PROGRESS → live `User_At_Base` → last confirmed → legacy) is implementable as a single ternary on the existing fields for AC-6.
- **`TDS_Trip_State.json` does not exist** in the live data directory (per the first-slice audit; `User_At_Base`, `Base_Arrival_Unix`, `Active_Geo_Latch`, `Current_Status` are spread across `setGlobal` calls in `Sandbox_Engine.js`). Slice 2's 0C work has a choice: either (a) use the existing `User_At_Base` / `Base_Arrival_Unix` globals as the de-facto trip-state record for the live-origin priority chain, or (b) introduce a `TDS_Trip_State.json` schema migration. Option (a) is consistent with the post-first-slice state and avoids a file-format change.
- **No `IN_PROGRESS` global exists.** The canonical spec §0.3 priority chain says "active `IN_PROGRESS`" should win before live `User_At_Base`. The codebase has `Current_Status` (e.g. `"Driving (Pitstop)"`, `"At Home"`, `"Lift"`) but no boolean `TripState.IN_PROGRESS`. Slice 2 can either: (a) approximate "active IN_PROGRESS" via a regex on `Current_Status` (e.g. `/(Driving|Walking|Public Transport|Lift)/i.test(currentStatus)`); or (b) leave the IN_PROGRESS slot empty for now and document it as a Phase 1 task. **Recommend (a) — the regex is good enough for AC-6's "live wins" test and matches the existing `Sandbox_Engine.js:380-385` code that derives travel mode from `Current_Status`.**
- **`AdHoc_Base` is a valid origin source** (set by `Return_to_Base.js` per the first-slice audit) but is not named in the spec §3 enum. The Sandbox already tracks it via `global('AdHoc_Base')`. Slice 2 should preserve this behavior without renaming.
- **`departurePolicy` and `actionType` overlap.** `Compiler.js:248` already special-cases `headLeg.actionType === "EOD_RETURN"` to force ASAP. The two concepts are not perfectly orthogonal: an `EOD_RETURN` is a return-to-base leg whose policy is always ASAP. The proposal should clarify: `actionType` is the leg kind (EOD_RETURN, EVENT, RECOVERY, PITSTOP, MANUAL); `departurePolicy` is the timing policy. Slice 2 emits the policy and Compiler reads it, but the spec is right that the policy is the authoritative source.
- **The first-slice verify-report's NEW WARNING** (`Dispatcher.js:50-52` returning `nowSec + RELEVANCE_EOD_SECS` for EOD returns) is a §6/deadline concern, not 0A/0C. Out of slice 2 scope.
- **First-slice GGA pre-existing violations** (`Compiler.js` `indexOf` on event IDs, missing structured JSON logging) remain in the live code. Slice 2's `Compiler.js` change touches the `isPrevBase` block (`Compiler.js:160-168, 247-256`); a careful GGA review of the surrounding `indexOf` calls is appropriate. Not a blocker.

## Open questions for the user (the orchestrator will ask after I return)

1. **Sandbox queue output shape.** The Sandbox emits a positional pipe-delimited queue via `setLocal('block_queue', queue.join("~"))` at `Sandbox_Engine.js:1222`; each queue row currently has 18 positional columns (mode, coords, mode, start, end, pitstopState, apiType, apiUnix, evId, evLoc, engineLateMins, currentLegStable, dropinStatusFlag, safeDesc, adHocArr, ...). The consumer is an external Tasker native that splits the columns into `block_step1`–`block_step16` plus `api_*` locals. The canonical spec §0.1 already names `block_step17`, `block_step18`, `block_step19` as the typed protocol. **Should slice 2:** (a) add a 19th column to the queue and emit `block_step19` as a separate `setLocal` (matching the spec's typed protocol — three new keys `block_step17` for duration, `block_step18` for distance, `block_step19` for policy; but `block_step17/18` are already filled by the API parser via `api_duration_secs` / `api_distance_miles`, so this is effectively just `block_step19`); (b) append a `~`-delimited suffix to the existing queue row (e.g. `...|ASAP` at the end) and have the consumer split it; (c) keep the queue unchanged and add a new `setLocal('block_departure_policy', "ASAP")` for the head leg only. **Recommend (a) for the head leg (matches the spec's typed protocol) and pass the policy as a single value; the body legs continue to derive their `depTarget` from the chain math.** The proposal should confirm.
2. **`TDS_Trip_State.json` file existence.** The canonical spec names it; the first-slice explore said it does not exist in the live data directory. Live state is in `User_At_Base`, `Base_Arrival_Unix`, `Active_Geo_Latch`, `Current_Status` globals. **Should slice 2:** (a) use those globals as the trip-state record (no schema migration, matches slice 1's minimal-change posture); or (b) create `TDS_Trip_State.json` as a new file in this slice (bigger scope, more writes, more risk). **Recommend (a) for AC-6's live-origin test.**
3. **`Override_Injector.js:9` vs `Appender.js:8` adapter convention mismatch.** `Override_Injector.js:9` reads `local('par1')` while `Appender.js:8` reads `local('final_return')`. Two adapters, two conventions. **Out of scope for slice 2** (0A/0C do not touch command handling), but flag for the second-slice proposal. The first-slice audit already called this out.
4. **`originSource` enum migration.** Spec §3 names seven valid origin source values. The codebase has no equivalent. **Should slice 2:** (a) leave the enum for Phase 1 (typed protocols) and use a single ternary on the existing fields; or (b) introduce the enum on a new field on each emitted leg. **Recommend (a) for AC-6's "live wins" test** — the spec is explicit that 0C is a behavioural invariant, not a schema migration. A future Phase 1 slice can land the enum.
5. **`Pitstop_Reconcile` interaction.** The Sandbox at `Sandbox_Engine.js:891-892` sets `simAtBase = true` after a handled pitstop. With AC-6, a live `User_At_Base = "false"` mid-pass should be able to override this — but only if the live read is consulted at that point. **Should slice 2:** (a) consult live `User_At_Base` once at pass start (idx=1) and trust it; (b) consult live `User_At_Base` at every event iteration in the master loop. **Recommend (a) — matches the first-slice semantics, keeps the diff small, and the spec §0.3 priority chain is consulted at pass start, not mid-pass.** A stale itinerary will only be re-evaluated on the next planning pass.
6. **Active IN_PROGRESS approximation.** Spec §0.3 names "active `IN_PROGRESS`" as the second-priority source. The codebase has no boolean trip-state flag. **Should slice 2:** (a) approximate via regex on `Current_Status` (e.g. `/(Driving|Walking|Public Transport|Lift)/i.test(currentStatus)`); (b) introduce a `TDS_Trip_State` global; (c) leave the slot empty. **Recommend (a) — it matches `Sandbox_Engine.js:380-385`'s existing logic and avoids a new global.**
7. **`TDS_Overrides.json` write.** `Compiler.js:421-425` writes `OVR['Depart_Memory']` to `TDS_Overrides.json` — a known single-writer violation that the first-slice verify-report flagged. Slice 2 must NOT add a new key to this file. **Confirm with the user:** slice 2 leaves the violation in place; Phase 3 consolidates the override store.

## Summary of the AC-1 and AC-6 closure path

- **AC-1:** `Sandbox_Engine.js` emits `departurePolicy` for every leg (head + chain). The decision rule (per spec §0.1) is: ASAP for between-event travel, attached chains, recovery, returns, manual travel, due/in-progress legs; JIT for first/base/future post-overnight unless active state supersedes it. `Compiler.js` consumes the explicit policy at `Compiler.js:247-256` and stops reconstructing it from `pitstopState`/`_IN`/`EOD_RETURN`. The `block_step19` slot is the typed-protocol carrier.
- **AC-6:** `Sandbox_Engine.js` consults the live origin priority chain at pass start: active manual trip (none today) → active IN_PROGRESS (regex on `Current_Status`) → live `User_At_Base` → last confirmed trip-state destination (no equivalent today; fall through) → legacy itinerary. When `User_At_Base === "true"` and the prior itinerary's tail leg says away, the live value wins and `simAtBase` is initialised to `true`. The harness test asserts this with synthetic fixtures.

## Affected Areas

- `Sandbox_Engine.js` — emit `departurePolicy` on every queued leg; consult live origin at pass start. Two code locations: the queue build at `Sandbox_Engine.js:1188-1189` (add the policy field) and the origin state machine at `Sandbox_Engine.js:438-449` (use live `User_At_Base` even when `oldItin.length > 0`).
- `Compiler.js` — consume the explicit `departurePolicy` at `Compiler.js:247-256`; remove or guard the `isPrevBase` reconstruction at `Compiler.js:160-168`. Read the new `block_step19` local.
- `harness/test_compiler_ac1.js` — new test (AC-1).
- `harness/test_sandbox_ac6.js` — new test (AC-6).
- No other live script is touched by slice 2.

## Risks

- **Mid-pass flip not covered.** Slice 2's recommendation is to consult live `User_At_Base` only at pass start. A flip mid-pass will not propagate until the next planning pass. The spec §0.3 priority chain is consulted "on a fresh pass" (the heading), so this is spec-compliant. The first-slice proposal considered this in the "Risks" section; slice 2 inherits the same risk. **Not a blocker.**
- **`Compiler.js` `isPrevBase` removal side effects.** The block at `Compiler.js:160-168` also feeds `hardFloor` recomputation at `Compiler.js:200-204` (the `else if (prevLeg.pitstopState === "forced" || ...)` branch). Replacing the reconstruction with the explicit `departurePolicy` does not break that branch — `hardFloor` is still updated by the explicit `prevEnd + depBuf` math at `Compiler.js:198` for non-dropin prev legs. **Confirm in the design phase that the explicit `prevEnd` math still fires when `block_step19` says JIT and the prev leg is an EOD_RETURN.**
- **`Sandbox_Engine.js` queue output is positional.** Adding a new column to the `block_queue` row requires a matching change in the external Tasker native consumer. If the consumer splits by column index, adding column 19 in the Sandbox without a matching update in the consumer will produce silent misreads. **The proposal must confirm the consumer is updated in the same Tasker action, or that the policy is passed via a separate `setLocal`.**
- **`Sandbox_Engine.js` size and test surface.** The script is ~72K bytes; running it in the `vm` harness for AC-6 will surface a long execution path. A minimum-viable AC-6 test (assertion on `simAtBase` after a pass, not on the full queue) is realistic; a full integration test is not.

## Ready for Proposal

**Yes.** Slice 2 has a clear scope (0A: emit `departurePolicy` in `Sandbox_Engine.js`, consume in `Compiler.js`; 0C: live origin priority at pass start), a known file footprint (two live files + two harness tests), and seven open questions for the user. The first-slice verify-report is the evidence baseline; the spec's INV-0.1 and INV-0.3 are the authoritative contracts. The proposal can be drafted immediately after the user resolves the seven open questions.
