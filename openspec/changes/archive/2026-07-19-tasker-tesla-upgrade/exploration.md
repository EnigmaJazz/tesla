## Identity & ownership drift

### ID parsing (§2)
**Violation: `id.split("_")[0]` is used in 4 live files.** Spec §2 says the separator is `lastIndexOf("_")`; the suffix is a base-36 Unix timestamp; substring splits are forbidden.

- `Sandbox_Engine.js:895` — `let coreId = evId.split("_")[0];` (used to build `routineKey = coreId + "^" + routeSig` for `Route_Defaults` lookup at lines 900, 903, 907)
- `Override_Injector.js:100` — `let coreId = targetId.split("_")[0];` (used for the `Route_History` key)
- `Appender.js:90` — `var coreId = baseId.split("_")[0];` (same `Route_History` key)
- The fourth live match is in `Override_Injector.js:65` (`items[j].indexOf(targetId) === -1`) — this is the substring-with-substring case called out in spec §10 (see below).

The fallback walker in `Alpha.js:386-395` correctly walks `idParts` from the end looking for a base-36 number in the 1B-2.5B range — that is the right pattern. The split-based calls above are bugs against the spec.

**Substring matching on IDs (§10).** `Finaliser.js:76, 91` does `completed.indexOf(ev.id) === -1` on a comma-separated `Completed_Dropins` string. If event ID `abc_2lkj` is in the list, `indexOf("abc")` returns truthy and `abc` will be treated as already completed. The deprecation rule from spec §10 ("exact-key maps, no `indexOf` membership checks") is violated. `Override_Injector.js:65` and `Appender.js:60` have the same pattern against comma-separated override arrays.

### Command handling (§9)
**There is no `TDS State Command` schema.** Commands are ad-hoc string literals parsed by `Override_Injector.js` (parses `targetEventId` and `overrideKey` from `local('par1')` / `local('par2')`) and `Appender.js` (parses a pipe-delimited `final_return` string with up to 3 fields). No `block_step17/18/19` typed fields exist — the spec's typed protocol for route duration seconds, route distance, and departure policy is not in the code. `Compiler.js` reads `block_step1, block_step2, block_step3, block_step4, block_step5, block_step7, block_step8, block_step9, block_step10, block_step12, block_step14, block_step15, block_step16` and `api_duration_secs, api_distance_miles, api_transit_steps` — that's 17 of the spec's variable slots, missing 17/18/19 (the typed departure policy block).

## Cache, cluster, override, API drift

### Route cache (§11)
- `Alpha.js:80` — `if (distM > 3000000 || distM > 1000000) continue;` — sanity bound on cache rows.
- `Alpha.js:122-167` — full Welford merge for `DRIVE` / `TRANSIT`, with a 60-min `tod` window (`Math.abs(tod - cTod); if (diff > 720) diff = 1440 - diff; if (diff <= 60)`) and `dayType` match. This is the "time-bucket matching for DRIVE/TRANSIT" the spec calls for.
- `Alpha.js:467-471` and `Sandbox_Engine.js:467-471` — `WALK` mode is **not** time-bucketed (any time matches). That's correct because walking time is mode-of-transport-bound, not time-of-day-bound.
- `Sandbox_Engine.js:472-484` — `DRIVE` / `TRANSIT` use the 60-min window with 15-min live override (`(nowSec - row.updatedSec) < 900`).
- `Sandbox_Engine.js:486-495` — third-tier RAM fallback (`Temp_Route_Cache.txt`).
- **TTL**: 15-min live override (`< 900s`) for drive/transit, otherwise bounded by the Welford mean ± 1 SD (`sd = (n > 2) ? Math.sqrt(oldM2 / (n-1)) : Math.max(120, oldMean * 0.15)` at `Alpha.js:144`). No explicit "stale after N days" TTL. The cache persists across generations.
- **Delimiter**: `~` (tilde) used in `RouteCache.txt`; `|` (pipe) is the row separator. The spec's "delimiter migration" callout is about migrating to JSON; the current text format is stable.
- **Bucket deletion**: there is no explicit "delete stale row" path; pruning happens via `Alpha.js:367-408` only for the override arrays, not the route cache. Cache drift accumulates.
- `getCachedTime` (`Sandbox_Engine.js:451-496`) has a dead branch: at line 453 it tries RAM first, then disk, but if the RAM branch is hit, the disk branch still runs because there is no `return` between them at the top of the function. The function re-checks RAM in the bottom fallback (line 486). Net effect: not a bug, but the inner RAM check at lines 455-464 is dead in the `isFuture` branch (already matched there) and only meaningful for non-future lookups.

### Overrides (§10)
- All override arrays in `TDS_Overrides.json` are comma-separated strings, not maps. Membership tests use `indexOf`. Examples:
  - `Override_Injector.js:52, 61, 65` — `valArr.indexOf(targetId)`, `OVR[arrName].indexOf(targetId)`, `items[j].indexOf(targetId)` — all substring.
  - `Appender.js:58, 60` — same pattern.
  - `Finaliser.js:76, 91` — `completed.indexOf(ev.id)` against `Completed_Dropins` (substring).
  - `Sandbox_Engine.js:28, 32, 182, 184, 199` — `getOvr('Forced_Lifts').indexOf(safeId)`, `ignoredLateness.indexOf(evId)`, `skippedEvents.indexOf(sId)`, `getOvr('Skipped_Pitstops').indexOf(evId)`.
- `Appender.js:75` and `Override_Injector.js` correctly build `coreId` with `split("_")[0]` for the route history key — this is the same forbidden pattern called out in §2.
- `Stop_Logger.js:30-39` uses `indexOf(newStopEntry)` against `Completed_Stops` for "preventing double-logging" — this is exact-string (full entry) so it is correct, but the surrounding membership checks (e.g. `Override_Injector.js:65`) are not.
- The string `Completed_Stops` is a stop-with-ordinal inventory, not a key→value map. Spec §14 wants `stop:<eventId>:<ordinal>` IDs; the current scheme is `<eventId>_<durationMinutes>` which conflates the ordinal and the duration in one field.

### API parser
- `API_Parser.js:96-102` — `if (isNaN(dur) || dur < 0 || isNaN(distM) || distM < 0 || distM > 5000000) { flash("⚠️ API Parser Fault: Invalid metrics."); let mockFallback = JSON.stringify({ durationSecs: 0, distanceMeters: 0, ... }); setLocal('api_return_json', mockFallback); ... return; }` — when an API response is malformed the parser returns a zero-metric mock, which the Compiler (`Compiler.js:45-66`) then routes through the haversine fallback for `ACTIVE_TRAVEL`. This is a **silent** rejection — no `STALE_API_RESPONSE_DISCARDED` log, no `generationId`, no event code.
- The `CLUSTER` path (lines 42-65) does not check if `res.routes[0]` is the same generation as the cluster payload; it sorts and writes to `TDS_Order_Cache.txt` and `TDS_Master.json` unconditionally. There is no generation-bound check.
- `temp_payload.json` is reset to `"{}"` on success (line 119) and on the malformed-response branch (line 100). OK.

### Cluster builder (§12)
- `Finaliser.js:201-237` — Multi-dropin clustering. Builds clusters with sequential + temporal boundaries (4h `lastDropinTime` gap creates a `TIME_GAP_ANCHOR` cluster at line 217; final cluster anchored to `EOD_ANCHOR` at line 234).
- **Duplicate destination** in a cluster: not explicitly checked. A cluster with two waypoints at the same coords would still be sent to the API as separate `intermediates` in `API_JSON_Build.js:29-34`.
- **Day-boundary crossing** in the cluster: `Finaliser.js:201-237` iterates `validEvents` and only pushes a cluster when `veEnd > nowSec` (line 211). A drop-in that ends before `nowSec` is dropped, but a drop-in that spans midnight is kept whole. There is no per-leg day-boundary cut inside the cluster.
- `Gatekeeper.js:75-85` honours `dropinOrder` (forced ordering via `#dropin:N` tag) by sorting in place and writing to `TDS_Master.json` directly — this is the spec's "no direct master writes by Gatekeeper" violation.

### Stops (§14)
- `Compiler.js:68-81` — `stopPadSecs` summed from `pendingStopsRaw` (comma-separated minutes, e.g. `"5,10"`), then `duration += stopPadSecs`. The number of stops is not preserved as an ordinal, only the total minutes.
- `Sandbox_Engine.js:208-240` — `getRemainingStops(evId, desc, completedRaw)`: parses `#stop:(\d+)` from the event description (note: minutes, not ordinals) and removes any that are present in `Completed_Stops` (which uses the `<eventId>_<minutes>` shape). The "minutes" field is reused as the ordinal surrogate. No `stop:<eventId>:<ordinal>` scheme.
- The separation between stop duration and route duration is **violated** in Compiler.js (see test #8). In Sandbox, route time and stop time are kept distinct at the simulation layer (`adHocObj.secs` is added on top of `simRouteSecs`), but the Compiler collapses them into one `durationSecs` for the published itinerary.

## Logging & tests

### Structured logging (§17)
**No structured JSON logging exists anywhere in the codebase.** `grep` for `console.log`, `writeFile.*log`, `TDS_Log`, `severity`, `generationId`, `component` returned no matches. All errors are surfaced via `flash(...)` (Tasker toast) or set into `setLocal('ui_return_msg', ...)` / `setLocal('step_conflict', ...)`. Required event codes from the spec (LIVE_BASE_OVERRIDES_LEGACY_ORIGIN, OVERNIGHT_BOUNDARY_CREATED, CROSS_DAY_CHAIN_REJECTED, SYNTHETIC_RETURN_SUPPRESSED, FUTURE_TRIP_NOT_DUE, STALE_TRIP_REJECTED, REDUNDANT_EOD_RETURN_REJECTED, ZERO_DURATION_LEG_REJECTED, DEPARTURE_POLICY_FALLBACK_USED, GENERATION_VALIDATION_FAILED, STALE_API_RESPONSE_DISCARDED) are not emitted anywhere.

### Test surface
- `openspec/testing-capabilities.md` is explicit: no unit, integration, or e2e runner; strict TDD is off. Manual Tasker execution is the only verification path.
- No `package.json`, no `node_modules`. Tasker's JSlet engine.
- A deterministic harness would require mocking `local()`, `global()`, `readFile()`, `writeFile()`, `flash()`, `setLocal()`, `setGlobal()`, and `Date.now()`. The current `codegraph_explore` + `Read` workflow is the only available "read-only" check, and it cannot exercise runtime paths.
- A possible harness shape: a `harness.js` that loads each satellite, monkey-patches the Tasker primitives, and replays JSON fixtures. No such file exists. This is a candidate for a future change.

## Spec drift not covered above

- **Sub-second DST safety.** All day comparisons use `setHours(0,0,0,0)` or `getDate()` (e.g. `Alpha.js:60-61`, `Dispatcher.js:85-86`). These are local-timezone comparisons and do break across a DST transition. The spec's "must be DST-safe" invariant is not enforced.
- **Negative-gap loop guard (test #10)** is the single biggest Phase 0 defect because it can fire on every planning pass after the first stale departure and burns background CPU. The fix is two lines in `Dispatcher.js` (skip the head if `headTimeSecs < nowSec` and look forward to the next future leg; or fall through to idle sync if none).
- **Block-step 17/18/19 are absent** (no `block_step17`, `block_step18`, `block_step19` reads in any file). The spec's typed departure-policy protocol has not landed.
- **`User_At_Base` is the only "trip state"** that lives in globals. There is no `TDS_Trip_State.json` and no Trip State Reducer file. State is split across `setGlobal` calls in `Sandbox_Engine.js:336-342` and ad-hoc `setGlobal` in `Return_to_Base.js`, `Depart_Now.js`, `Compiler.js:215-217`.
- **`TDS_Action_Lock.json` is a single-bit lock** (driving/manual-routing flag), not a session log. The spec's `TDS_Action_Sessions.json` would carry per-session metadata.
- **No `TDS_Run_Manifest.json` exists.** There is no generation-bound artifact; the route cache, override file, and master file have no shared generation ID linking them.
- **`Route_Defaults` and `Route_History` are stored inside `TDS_Overrides.json`** (per `Override_Injector.js:31-32`, `Appender.js:30`), not in a dedicated `TDS_Routine_Preferences.json` as the spec calls for. The override handler therefore owns two separate concerns in the same JSON.
- **Silent fallback at `API_Parser.js:96-102`** returns `durationSecs: 0` to the Compiler. The Compiler's `apiType === "ACTIVE_TRAVEL"` branch (lines 45-66) will then run the haversine fallback and produce a non-zero duration. For a non-active-travel call, the published itinerary gets a 0-second route — directly contradicting the spec's "no zero-duration published travel leg" rule. The mock fallback needs to either propagate a real "could not resolve" event code or skip the leg.
- **`Override_Injector.js:9` reads `local('par1')` for `idx`** while `Appender.js:8` reads `local('final_return')` for the same logical concept. Two adapters, two different local-variable conventions, same target array. The spec wants a single `TDS State Command` envelope.
- **`setGlobal('TDS_Lateness_Halt', 'true')` is set in 6 places** (`Sandbox_Engine.js:762, 856, 927, 1143`, plus `Compiler.js`/`Finaliser.js` reads) with no event code. A halt currently means a single "🛑 SIMULATION HALTED" string in Dashboard — no audit trail of which rule fired.

## Open questions for the user

- **Spec source file** — the orchestrator passed the spec inline; no `openspec/specs/*.md` exists yet. Should we add `openspec/specs/itinerary/spec.md` (or similar domain) at proposal time, or treat the inline spec as authoritative for Phase 0 only?
- **Priority for Phase 0 first slice** — tests #8 (stop padding), #9 (stale departure), #10 (idle sync) are the three FAIL items. The user can land all three in one Compiler/Dispatcher patch, or in two: a single Compiler edit (test #8) and a single Dispatcher edit (tests #9 + #10). Which shape do they want?
- **TDS_Run_Manifest.json** — the spec names it, but no script writes it. Is the intent to add it as part of Phase 0, or is it a later-phase concern? It is the foundation for the `generationId` event-code field, so landing it unlocks §17 logging.
- **Timezone for day boundaries** — every day comparison uses `Date` local methods. The spec says "must be DST-safe" but does not name a timezone source. Is the system timezone acceptable, or do we need a `global('TDS_Timezone')`?
- **Are the `_archive/2026-07-19-baseline/Backup/*.js` files in scope for review?** They are byte-identical to the live scripts at version V14.4/V15.1/V16.5 baseline. They are not loaded by the live engine but they exist on disk. Proposal should explicitly say "ignore" or "delete".
- **Is `Override_Injector.js` a "command adapter" that should NOT live inside the override-handler single-writer slot?** Today it writes to `TDS_Overrides.json` directly. If it stays an adapter, the spec's single-writer contract should be amended to add it; if it should route through a handler, that is a refactor for later phases.
